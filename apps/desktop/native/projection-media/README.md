# Shared projection media transport (work in progress)

This module builds on the merged local projection foundation (#987). It supplies the shared host media backend and an internal adapter for actual App projection resources. The cloud device responder now has an internal authenticated signaling adapter. The product viewer entry point remains closed.

The backend pins [Pion WebRTC v4.2.26](https://github.com/pion/webrtc/releases/tag/v4.2.26), uses an H.264 RTP video track and a reliable ordered input DataChannel, and configures only STUN discovery on the host. Explicit relay candidates are rejected in remote descriptions, and known relay types in the selected pair are checked before application traffic. This does not prove the peer has no TURN hop: its allocation can appear as a peer-reflexive candidate. The viewer must also disable TURN; the free tier must not issue TURN credentials. The internal adapter binds App/task/target/page-epoch authority and routes execution acknowledgements from the owning input driver. Sending bytes does not mean native input was applied.

SDP must travel over an authenticated channel with integrity protection. Pion checks DTLS fingerprints against the accepted SDP; an unauthenticated description is not authority for an App, task or device.

`go test -race ./...` checks an actual local ICE/DTLS/SRTP/SCTP connection, ordered bidirectional control, RTP payload delivery, close, explicit relay refusal and inbound control text/size bounds. The encoder tests feed three raw BGRA frames into FFmpeg, send H.264 RTP across the encrypted connection, inspect the received SPS/VUI with the adjacent `ffprobe` binary, decode the received stream with FFmpeg, and verify pixel colors and order. RGB is converted to limited-range BT.709 and the bitstream explicitly declares the same matrix, range, transfer and primaries, so browser decoders do not choose a platform-specific default. Cancellation waits for the encoder process and its private pipe reader to exit.

FFmpeg emits size-delimited AVC access units over its stdout pipe using FLV framing; this container never goes over the network. Go bounds each tag, converts AVCC NAL units to Annex-B, and uses Pion's H.264 payloader to packetize RTP. There is no encoder UDP listener for another local process to inject into. Explicit access-unit sizes also let one frame finish without waiting for the next frame's start code. A large-frame test verifies fragmentation, one marker/timestamp per access unit and successful decoding after reassembly.

`GUGU_TEST_CHROMIUM=/absolute/path/to/chromium go test -race -tags browser ./...` additionally starts an isolated headless browser and verifies that its video track decodes the same three colors onto a canvas. Browser and encoder failures include their bounded diagnostics, and both child processes are awaited during cleanup. This test does not operate an installed Gugu instance or a user's browser.

`VideoEncoder` associates each source sequence with its actual encoded RTP timestamp, allowing only one frame in flight. The browser test compares that receipt with `requestVideoFrameCallback` metadata, including different frames with identical pixels. An encoder receipt alone never enables input: the host must verify the viewer's decoded-frame acknowledgement and its current target generation.

The native wire reader retains one raw-frame slab and waits for an explicit return before reading into it again. `VideoEncoder` retains a separate reusable copy of its last successfully encoded picture. Those two full-frame buffers are allocated per stream rather than per frame; encoded access units, browser buffers and Electron's bitmap copy still have their own allocations.

Authenticated RTCP PLI is coalesced into one pending request. The helper services recovery at most once per second, including while the host is idle and no decoded-frame acknowledgement exists. It joins the old FFmpeg process, starts an independent IDR from the retained picture and reuses the stream's RTP packetizer, preserving SSRC, sequence numbers and timestamp progression. An uncertain or failed source write is never replayed. A recovered frame receipt has `recovery: true`, the same source `sequence`, and a new `rtpTimestamp`. The host receives no extra `encoded` IPC response for this resend. A viewer must correlate recovery by that new decoded timestamp; accepting a resend must never authorize input against a different source sequence or target generation. This native prerequisite does not activate the product viewer.

The tests drop the initial IDR before SRTP and leave the host idle: actual Chromium requests recovery and decodes the correct color with the exact recovery timestamp. The helper test independently sends PLI over RTCP, verifies a decodable IDR without new host input/ACK, and bounds a burst of 100 requests. Other tests guard raw-buffer ownership/reuse and RTP continuity across three encoder replacements.

The native `cmd/projection-media` helper uses length-prefixed IPC: kind 1 carries bounded JSON commands/events, while kind 2 carries an eight-byte big-endian source sequence followed by tightly packed BGRA. Host-resolved executable paths and encoding configuration are launch arguments; the peer cannot supply them. The helper produces an offer, accepts one answer, exchanges control bytes and reports encoding receipts. Video and frame metadata travel on the direct WebRTC connection. A `sent` receipt means SCTP admission, never native execution. EOF, cancellation, media failure and explicit close terminate the media connection and encoder.

Build the helper with `go build -race -o /absolute/path/to/helper ./cmd/projection-media`, then set `GUGU_TEST_MEDIA_HELPER` and run `go test -race -tags 'browser helper' ./...`. The additional test starts the actual child, exchanges its SDP with another peer, writes raw frames through its binary pipe, verifies SRTP timestamps and metadata, exchanges Unicode control bytes, and waits for a clean close receipt and process exit.

The helper selects between input and cancellation. Its inherited blocking stdin is isolated behind a cancellable pipe, so SIGTERM/SIGINT work while the parent keeps stdin open. `ServeMedia` requires an input whose `Close` interrupts `Read`; its CLI wrapper provides this pipe. EOF closes it cleanly. A warm frame has a three-second encoding deadline. The first frame of each FFmpeg process, including a PLI replacement, has a separate eight-second startup budget; host receipt deadlines must leave additional time beyond it. Both preserve distinct timeout causes and any shorter parent cancellation; cancellation after admission closes the stream rather than relabeling or replaying an uncertain frame. FFmpeg is given a minimal environment and has a bounded `WaitDelay` for pipe cleanup. A nonzero encoder exit retains its stderr tail and exit status, including when stdout closes or an in-flight stdin write fails first.

The host supplies an absolute trusted FFmpeg executable with libx264. The encoder uses [`-fps_mode passthrough`](https://ffmpeg.org/ffmpeg.html#Advanced-Video-options), supported by FFmpeg 5.1 or later; the tested FFmpeg 9.0.2 no longer accepts `-vsync`. The advertised baseline H.264 level 3.1 is enforced before a process starts: at most 3,600 rounded macroblocks per frame, 108,000 per second, and 14 Mbit/s ([ITU-T H.264, Annex A](https://www.itu.int/rec/T-REC-H.264/en)). For example, 1280×720 at 30 fps is admitted; 1080p or 720p at 60 fps requires future negotiation and is refused.

`web/viewer.mjs` receives the video track in a browser without TURN configuration. It pairs a frame receipt only with the currently decoded `requestVideoFrameCallback` RTP timestamp, invalidates a replaced picture immediately, and ignores receipts for pictures no longer visible. The drawing callback receives a matching frame or `null`; it is responsible for drawing before forwarding a host-authorized acknowledgement. Control callbacks can respond before startup returns, without capturing a not-yet-assigned viewer handle. Binary or oversized control, wrong geometry, unreliable channels, lost connections and cancellation close the viewer. The real Chromium test imports this receiver, draws each frame to a canvas, checks its pixels and sends the matching receipt back; state fixtures separately cover late receipts, early control and cleanup failures.

The Node host client and `ProjectionSignals` remain internal primitives; they do not authenticate a peer by themselves. The cloud-only `projection.*` device adapter captures the actual main-process login and fresh device/runtime lease, then requires a random 256-bit proof returned on that exact private asker connection. A request cannot supply its owner or resource-host device identity. The viewer is authenticated as an owner connection, not as a physical device inferred from its claimed id. SSH and the common un-attached topic cannot open this adapter. Ordinary RPC reply caching is bypassed so a stale request id cannot bypass a live proof/page check.

The source registry still checks the installed/enabled App, its exact version, capability, task and source. Page bindings advance monotonically, invalidate the previous epoch before draining, and retain cancellation tombstones to reject a bind arriving after cancellation. Closing releases the private proof explicitly; account/runtime loss or actual asker detach also revokes it. Cleanup waits for admitted input, driver disconnect and physical helper exit, then releases authority. The outer runtime tracks asynchronous responder cleanup through host shutdown.

Each viewer pipe owns an independent realtime client: the SDK reuses channel objects by topic name, so sharing a client across independently closed pipes would mix their subscriptions. Its token provider stays bound to the captured account. Cancellation interrupts authentication and subscription waits; any late pipe is closed, with cleanup failures reported.

The main-only viewer client derives its App/task/target from the actual webContents binding. It keeps the connection proof and per-binding control key out of the guest. Before every ACK/input signature it checks that page, grant and login/runtime lease again. The resource host verifies HMAC-SHA256 over the binding, source and exact control bytes before parsing the underlying packet; bare, altered, foreign-source and old-binding control is refused. Encoded frames and native input still use direct WebRTC, never the cloud RPC channel. The optional browser `prepareControl` callback asks its trusted host for an individual signed packet, with a bounded ordered queue and cancellation; it has no key.

The device factory accepts only host-resolved executable paths. The production resolver requires the helper and FFmpeg under the application resources directory and fails closed when they have not been packaged. There is no App/preload verb or product UI entry for this internal client yet. Fixture authority tests alone do not prove real private-channel or two-computer operation.

The unconditional `Projection native media` CI job builds a race-enabled helper and runs all native, browser and helper tests three times with actual FFmpeg and Chromium. This job is required by the aggregate gate. Test binaries can be selected with `GUGU_PROJECTION_FFMPEG` and `GUGU_TEST_CHROMIUM`. Production binary packaging, codec-level and geometry negotiation, large-text transfer, cross-device connectivity, private-channel integration acceptance and product UI integration remain unfinished. No encoded bytes or inputs use the signaling channel, and there is no relay or image-stream fallback.

Pion WebRTC v4.2.26 is [MIT licensed](https://github.com/pion/webrtc/blob/v4.2.26/LICENSE); its modules and checksums are pinned in `go.mod`/`go.sum`. Dependencies retain their own licenses. The upstream [RTP-to-WebRTC example](https://github.com/pion/webrtc/tree/v4.2.26/examples/rtp-to-webrtc) documents the encoder/transport boundary.

Remaining integration prerequisites include handling recovery receipts in the product receiver, real private-channel/two-computer acceptance, and product packaging. Each feed constructs its own decoder and joins any late-created media process before rejecting cancelled initialization. Distinct initialization and cleanup failures are retained together. Before a product entry point is enabled, decoded image dimensions and main-thread work need tighter bounds, and odd or oversized window geometry needs padding or scaling instead of rejection. The remaining native follow-ups from #1011 are cancellable helper stdout under a non-reading parent, removing the test-loopback option from production builds, and time-based periodic keyframes. These are not asserted complete by the native PLI and raw-buffer work.

Service-level ownership is guarded independently of the reader: a deliberately blocked encoder subprocess verifies every raw input byte while the host pipelines a second picture. An additional retained-IDR decode verifies that cached pixels do not alias caller storage. The helper test rejects any unsolicited `encoded` receipt after recovery instead of skipping it while waiting for another event. Its short no-recovery observation is 150 ms; recovery completion uses a separate generous deadline. Startup tests use an owned delayed process that replaces itself with the real FFmpeg, so cancellation does not leave a sleeping subprocess behind. They exercise initial startup, replacement startup, the finite startup deadline, the warm-frame deadline, and shorter parent deadlines.

The opt-in `projection-media.real-electron.test.ts` exercises an installed fixture App and its real capability checks: hidden window capture → NativeImage normalization → resource feed → native H264 → isolated Chromium paint. It verifies two decoded colors and matching source/RTP receipts, one Unicode input execution, reused normalized storage, and App revocation with driver/helper cleanup. It needs `GUGU_BROWSER_REAL_ELECTRON`, `GUGU_TEST_MEDIA_HELPER`, `GUGU_PROJECTION_FFMPEG` and `GUGU_TEST_CHROMIUM` as explicit executable paths. Its local HTTP server is test signaling only; it does not implement authenticated device RPC or prove cross-device operation. The macOS session job runs this factory fixture after installing its actual browser and encoder and building a race-enabled helper; its first successful hosted execution was verified on `fe003cdc`.

Host authorization resolvers receive the binding cancellation signal and must honor it during asynchronous authority lookup. This allows retarget/disposal to cancel the lookup before waiting for it, and prevents a late result from starting an old page epoch. A resolver that ignores this internal contract can still delay cleanup; network authorization adapters must propagate the signal.

After a clean `closed` receipt, the Node client allows two seconds for physical helper exit, then sends SIGTERM and escalates to SIGKILL after another two seconds. It waits for physical exit and reports the timeout or forced kill instead of treating the receipt as completed cleanup. `ProjectionSignals` drains admitted input, awaits driver disconnect, closes media, and attempts lease release even after a failure. An explicitly awaited close rejects with the first cleanup failure. Background helper/control/handshake and cleanup failures converge on the optional `onError` callback; its default writes bounded diagnostics to stderr. Later cleanup failures are also reported, and expected binding/grant cancellation is suppressed.

The factory fixture also checks an actual native helper that returns after cancellation: it must physically exit before initialization rejects. A separate overlap probe uses actual installed App source grants and NativeImage with deliberately blocked encoder callbacks, proving concurrent feeds keep separate pixel storage and reuse only their own returned buffers. The overlap probe does not claim two simultaneous network streams.

The factory fixture additionally runs the real device adapter, requester/responder, NativeImage, helper and Chromium receiver, with two decoded colors, host-signed Unicode input executed once, and retarget cleanup. Its RPC pipe is an isolated in-memory test transport; it does not claim authenticated cloud traffic. The real webContents binding lookup has a separate retarget behavior test. A manual two-account shared-test probe confirmed private-topic read isolation; the SDK broadcast result alone was not treated as proof of write refusal.
