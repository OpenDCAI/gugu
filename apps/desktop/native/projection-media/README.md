# Shared projection media transport (work in progress)

This module builds on the merged local projection foundation (#987). It supplies the host media backend shared by desktop and the headless server; it is not yet wired into App resources or device signaling.

The backend pins [Pion WebRTC v4.2.26](https://github.com/pion/webrtc/releases/tag/v4.2.26), uses an H.264 RTP video track and a reliable ordered input DataChannel, and configures only STUN discovery on the host. Explicit relay candidates are rejected in remote descriptions, and known relay types in the selected pair are checked before application traffic. This does not prove the peer has no TURN hop: its allocation can appear as a peer-reflexive candidate. The viewer must also disable TURN; the free tier must not issue TURN credentials. The host must still bind App/task/target/epoch authorization and interpret execution acknowledgements. Sending bytes does not mean native input was applied.

SDP must travel over an authenticated channel with integrity protection. Pion checks DTLS fingerprints against the accepted SDP; an unauthenticated description is not authority for an App, task or device.

`go test -race ./...` checks an actual local ICE/DTLS/SRTP/SCTP connection, ordered bidirectional control, RTP payload delivery, close, explicit relay refusal and inbound control text/size bounds. The encoder tests feed three raw BGRA frames into FFmpeg, send H.264 RTP across the encrypted connection, inspect the received SPS/VUI with the adjacent `ffprobe` binary, decode the received stream with FFmpeg, and verify pixel colors and order. RGB is converted to limited-range BT.709 and the bitstream explicitly declares the same matrix, range, transfer and primaries, so browser decoders do not choose a platform-specific default. Cancellation waits for the encoder process and its private pipe reader to exit.

FFmpeg emits size-delimited AVC access units over its stdout pipe using FLV framing; this container never goes over the network. Go bounds each tag, converts AVCC NAL units to Annex-B, and uses Pion's H.264 payloader to packetize RTP. There is no encoder UDP listener for another local process to inject into. Explicit access-unit sizes also let one frame finish without waiting for the next frame's start code. A large-frame test verifies fragmentation, one marker/timestamp per access unit and successful decoding after reassembly.

`GUGU_TEST_CHROMIUM=/absolute/path/to/chromium go test -race -tags browser ./...` additionally starts an isolated headless browser and verifies that its video track decodes the same three colors onto a canvas. Browser and encoder failures include their bounded diagnostics, and both child processes are awaited during cleanup. This test does not operate an installed Gugu instance or a user's browser.

`VideoEncoder` associates each source sequence with its actual encoded RTP timestamp, allowing only one frame in flight. The browser test compares that receipt with `requestVideoFrameCallback` metadata, including different frames with identical pixels. An encoder receipt alone never enables input: the host must verify the viewer's decoded-frame acknowledgement and its current target generation.

The native `cmd/projection-media` helper uses length-prefixed IPC: kind 1 carries bounded JSON commands/events, while kind 2 carries an eight-byte big-endian source sequence followed by tightly packed BGRA. Host-resolved executable paths and encoding configuration are launch arguments; the peer cannot supply them. The helper produces an offer, accepts one answer, exchanges control bytes and reports encoding receipts. Video and frame metadata travel on the direct WebRTC connection. A `sent` receipt means SCTP admission, never native execution. EOF, cancellation, media failure and explicit close terminate the media connection and encoder.

Build the helper with `go build -race -o /absolute/path/to/helper ./cmd/projection-media`, then set `GUGU_TEST_MEDIA_HELPER` and run `go test -race -tags 'browser helper' ./...`. The additional test starts the actual child, exchanges its SDP with another peer, writes raw frames through its binary pipe, verifies SRTP timestamps and metadata, exchanges Unicode control bytes, and waits for a clean close receipt and process exit.

The helper selects between input and cancellation. Its inherited blocking stdin is isolated behind a cancellable pipe, so SIGTERM/SIGINT work while the parent keeps stdin open. `ServeMedia` requires an input whose `Close` interrupts `Read`; its CLI wrapper provides this pipe. EOF closes it cleanly. A frame has a three-second encoding deadline; cancellation after admission closes the stream rather than relabeling or replaying an uncertain frame. FFmpeg is given a minimal environment and has a bounded `WaitDelay` for pipe cleanup. A nonzero encoder exit retains its stderr tail and exit status, including when stdout closes or an in-flight stdin write fails first.

The host supplies an absolute trusted FFmpeg executable with libx264. The encoder uses [`-fps_mode passthrough`](https://ffmpeg.org/ffmpeg.html#Advanced-Video-options), supported by FFmpeg 5.1 or later; the tested FFmpeg 9.0.2 no longer accepts `-vsync`. The advertised baseline H.264 level 3.1 is enforced before a process starts: at most 3,600 rounded macroblocks per frame, 108,000 per second, and 14 Mbit/s ([ITU-T H.264, Annex A](https://www.itu.int/rec/T-REC-H.264/en)). For example, 1280×720 at 30 fps is admitted; 1080p or 720p at 60 fps requires future negotiation and is refused.

The unconditional `Projection native media` CI job builds a race-enabled helper and runs all native, browser and helper tests three times with actual FFmpeg and Chromium. This job is required by the aggregate gate. Test binaries can be selected with `GUGU_PROJECTION_FFMPEG` and `GUGU_TEST_CHROMIUM`. Production binary packaging, codec-level and geometry negotiation, host input acknowledgement integration, large-text transfer, cross-device connectivity, authenticated device signaling and App integration remain unfinished. No encoded bytes or inputs use the signaling channel, and there is no relay or image-stream fallback.
